# フロントエンドの性能設計と検証

入力、一覧、非表示ビュー、初期読み込みを設計・変更するときに使う再利用可能な知見です。個別PRの作業ログや改善率は保存せず、確認できた失敗パターンと検証方法を残します。

責務の境界は [ARCHITECTURE.md](../../ARCHITECTURE.md)、CSSの配置とカスケードは [STYLING_STRATEGY.md](../../frontend/STYLING_STRATEGY.md)、実描画の確認は [frontend_visual_verification.md](frontend_visual_verification.md) を参照してください。

## 設計時に決める境界

| 症状 | 確認する境界 | 再発防止 |
| --- | --- | --- |
| 入力欄が重く、一覧の件数で悪化する | 入力状態の所有者、Contextの購読、親からの再描画 | 入力に関係しない一覧・閉じたモーダル・非表示ビューへ更新を広げない |
| コードを含む文書で、普通の文章入力まで重い | 文書更新とコード解析・サニタイズ | 変更のないブロックの解析結果を再利用し、位置は現在の文書から求める |
| 入力や画面復帰でlayout処理が増える | 高さ調整の所有者、DOMの読み書き、observerの有効期間 | 重複計測をまとめ、表示が必要な間だけ購読する |
| 初期表示が全ページで重い | 共通CSS・画像・先読みの開始時点 | ページ専用の負担を共通の初期経路から外し、必要になる前に準備する |
| 同じAPIを初回に複数回取得する | mount、表示セクション、言語確定の各effect | 初回取得を一つの経路にまとめ、再訪・再取得の条件を明示する |

最初に「どの状態変更が、どのビュー・計測・取得を更新する必要があるか」を決めます。見た目や操作を維持する改善では、アニメーション値、対応言語、保存タイミング、入力方法を変える前に、不要な仕事の削減を検討します。

## Reactの更新範囲

- Contextを分けるだけでは、状態を持つ親の再描画による子の更新を止められません。Providerの値と、その外で組み立てるchildren・propsの参照が安定する境界を確認します。
- 一覧の`memo`化は、カードの内容に影響しない入力から切り離す場合に使います。配列・既定の空オブジェクト・コールバックを毎回作ると、境界を越えて更新が伝わります。依存している値を省いてコールバックを固定すると、古い状態を使う別の不具合になります。
- CSSで非表示にしたコンポーネントも、マウントされていれば購読や処理が続きます。閉じたモーダル・別ビューの更新とobserverを見直し、下書き、選択、スクロール、退出アニメーションに必要な状態は保持します。
- 安定したコールバックから最新の処理へ委譲する場合、render中のref更新で未確定の状態を公開しないでください。commit後に反映し、Suspense等で新しい描画が保留されても、確定済み画面の操作が正しいことを検証します。

## 解析・DOM計測・通信の重複

- 文書の変更を理由に、すべてのコードブロックへ言語自動判定・ハイライト・サニタイズを毎回実行しないでください。結果に影響する本文と言語を再利用の条件にし、入力に関係する部分だけ解析します。キャッシュの寿命を限定し、削除済みの文書を無制限に保持しません。
- ハイライトの相対位置と文書内の絶対位置を分けます。文章の挿入、同じコードの重複、ブロックの移動・削除、原文切替・文書置換でも、現在の位置と安全な出力を維持する必要があります。言語を減らしたり自動判定を変えたりして得た速さとは区別します。
- 入力欄の高さ調整は所有者を一つにします。`scrollHeight`等の読み取りを重複させず、必要な計測をまとめてから高さ・overflowを反映します。非表示中のobserverを止める場合も、表示復帰の最初の描画と退出中の寸法を確認します。
- データ取得はmount・セクション切替・言語変更のどこが責任を持つかを決めます。保存済み言語がURLと違う場合、取得前に必要な初期状態を確定させます。通常表示、セクションへの直リンク、再訪、設定取得失敗を確認し、重複防止のために必要な更新まで止めないでください。

## 初期読み込みと準備

- ページ専用CSSを共通バンドルへ追加する前に、実際の利用箇所を確認します。移動する場合は、完全なセレクタ、同じ要素に付くクラス、詳細度、`!important`、同名keyframesやCSS変数まで確認します。クラス名の重複だけで安全性を判断しません。
- CSSのダウンロード完了と、表示へ適用される時点は別です。先読みしただけで準備完了とせず、直接表示とクライアント遷移の双方で、専用CSSが整う前の描画がないことを確認します。離脱後にもCSSを保持する仕組みでは、別ページへの影響を確認します。現在の読み込み方はCSS方針に従います。
- ルートの先読みを初期ロードと入力へ無条件に並列投入しません。待機時間には順次準備し、ユーザーがメニューを使う時は早めに開始します。タッチ、キーボード、Shadow DOM内のイベントも対象にし、失敗時の再試行とtimer・idle callback・listenerの解除を検証します。
- 画像の転送量を減らす場合、表示寸法・alpha・見える画素を確認します。「可逆形式」という名称だけで同じ表示と扱わず、デコード結果と実ブラウザの描画を比較します。
- 初期経路から仕事を外す改善は、セッション全体からその仕事をなくす改善とは限りません。初期バンドル、遅れて取得するアセット、取得後の解析・適用を分けて報告します。

## 性能比較の手順

1. **再現条件を固定する。** 比較元と変更後のコミット、本番ビルド、データ件数・内容、SSRの応答、認証、言語、テーマ、viewport、CPU・回線条件を記録します。外部サービスの変動や実際の書き込みは固定fixtureで排除します。開発サーバーの時間を本番性能と同一視しません。
2. **同じ操作を保証する。** 入力文字列・間隔・位置・モードを揃えます。最後のclick/focus操作の後にカーソル位置を確定し、入力後の文書内容もassertします。異なるコードや段落へ入力した比較は採用しません。
3. **処理を分けて測る。** JS実行、main task、style再計算、layout、長いtask、通信回数・サイズを確認します。CDPの区間差分は入力中の総処理時間であり、1文字の応答時間ではありません。イベント計測の記録閾値も記載します。
4. **時間差には繰り返しと揺れを示す。** 同条件で各3回以上を逐次測定し、中央値と各回の値を残します。測定中に別のブラウザ検証・ビルド等を並走させません。小さな差を確実な改善と断定せず、都合のよい結果が出るまで測り直しません。
5. **読み込みの状態を揃える。** 新しいブラウザcontextと既に準備した状態を区別し、先読みから遷移までの待ち時間も固定します。リクエストのモック・ルーティングがキャッシュに影響する場合は条件を記録します。未圧縮サイズ、圧縮された本体、ヘッダー込みの転送量を混同しません。
6. **初期表示と操作の両方を確認する。** 入力だけでなく、初回訪問、メニューからの遷移、画面復帰、セクションへの直リンクも確認します。静止画が整っていても、遷移途中の1フレームだけCSS未適用になる場合があります。
7. **結論の範囲を記す。** CPU減速付きChromiumは実機スマホの再現ではありません。固定データでの結果と、本番データ・実機・バックエンド応答を含む結果を区別します。スクリーンショット差の原因は、位置・style・画像データ等で確認できた範囲だけ述べます。

## 回帰を防ぐ確認

- 再描画の境界は、実際の状態所有者・Provider・コールバック経路に対し、無関係な入力で更新が伝わらないことと、必要な変更は反映されることの両方を確認します。
- 解析の再利用は、呼び出し回数と出力の一致で確認します。位置変更、言語変更、文書置換・undo等の操作を、変更に対応する既存テストと合わせて担保します。
- 通信・先読み・observerは、開始条件、重複、再訪、失敗、解除をテストします。CIには環境で揺れる経過時間の一律閾値を追加せず、実装上の不要な仕事が再び増えない条件を使います。
- 見た目や操作は、PC・タッチ端末幅、ライト・ダークで実際に操作し、位置・サイズ・主要style、保存・下書き・入力、アニメーションを確認します。スクリーンショットの目視とハッシュ比較を行い、画素差を省略したり、すべてを描画環境の差と決めつけたりしません。
