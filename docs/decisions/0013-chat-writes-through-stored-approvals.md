# 0013: チャットからの書き込みはサーバーに保存した承認待ちアクションを経由する

## 状態

採用

## 背景

チャットの AI にメモの作成・追記・書き換えを任せたいという要望に対し、既存の枠組みは2つありました。1つは画面操作エージェント（`docs/architecture/system_design_deep_dive.md` 第14節）で、操作計画をフロントエンドが受け取り、確認モーダルを経て画面上の操作として実行します。もう1つは MCP 経由のメモ操作（`services/mcp_memo_service.py`）で、外部 AI クライアントが OAuth の同意とスコープの範囲で直接実行します。どちらもチャットの通常会話の中でモデルが自発的にメモを書く、という今回の要件には合いません。画面操作エージェントは「その画面の操作」を前提にした別のリクエスト・レスポンス契約であり、チャットの生成ループとは別物です。MCP は接続元がすでに同意済みの外部クライアントであり、会話の途中で人が読んで判断する前提を持ちません。

チャットの生成はストリーミングの1本のループ（[ADR 0009](0009-single-turn-state-chat-loop.md)）で動き、モデルはツール呼び出しの結果を見ながら次の判断をします。この中で書き込みをその場で実行してしまうと、次の3つの問題が起きます。第一に、間接プロンプトインジェクション（Web検索結果や取得した外部ページの本文に埋め込まれた指示）が、利用者の確認なしにメモの書き換えへつながる恐れがあります。第二に、ストリームの途中停止や失敗時に「実行されたかどうか」が生成の成否と結び付いてしまい、回復の設計（[ADR 0006](0006-long-running-chat-completion-recovery.md)）と衝突します。第三に、フロントエンドが「承認するかどうか」を尋ねる余地がなく、確認なしの書き込みを許すか、書き込み機能自体を諦めるかの二択になります。

## 判断

- 書き込みツール（PR1 の範囲では `memo_create`／`memo_append`／`memo_edit`）は生成中に実行しません。呼ばれると `services/chat_workspace_tools/` が引数を検証して提案（Proposal）を作り、`services/chat_tool_approval_service.py` が `chat_tool_approvals` に `status=pending` の行を1件保存します。カードの形（`ToolApprovalApi`）は `services/response_models.py` を正本にし、回答メッセージの `tool_approval` パーツとして末尾に付けます。実行はサーバー側で、利用者がカードから承認した後にだけ行います。
- 読み取りツール（一覧・検索・全文読み取り）は今までの検索・根拠読み取りツールと同じく、その場で実行して結果を根拠として渡します。書き込みだけを承認待ちにするのは、読み取りは取り消し不要で、書き込みだけが取り消しにくい変更（`docs/architecture/security_model.md` の「ツールと操作のリスク分類」）だからです。
- 承認カードは、対応する既定スキル（「メモ」、`users.memo_tools_skill_enabled`）が ON のときだけ、ログイン利用者の通常ルームのストリーミング生成に限って提示します。ゲスト・一時ルーム・非ストリーミング経路・スキル OFF では、ツールの定義もスキルの指示も渡しません。生成UIの既定スキルと同じ理由（Skill を切ったら関連する指示が何も残らないようにする）です。
- 利用者は、ツールごとに「常に承認」を選べます（`chat_tool_auto_approvals`、利用者とツール名の組で一意）。付与済みのツールは提案の時点で実行しますが、そのターンが Web 検索・外部ページの取得・貼り付け URL・他人の公開投稿など外部の内容を読んでいた場合は、常に承認を保持していても自動実行せず、通常の承認待ちカードへ戻します。間接プロンプトインジェクションで読んだ外部の文面が、確認なしの書き込みを引き起こさないようにするためで、付与そのものは取り消しません。対象が共有中のメモであるときも常に承認を許可しません。
- 承認カードが1枚でも残ったターンは、以後そのターンでツールを1つも提示せず、次のモデル判断は回答（force_answer）にします。新しい終了フェーズは作らず、ADR 0009 の単一ループのまま「ツールが無ければ回答する」という既存の規則に乗せます。回答には「何を提案し、承認待ちであること」だけを書かせ、実行済みであるかのような言い回しや、承認カードの代わりの選択ボタンを専用の指示で禁じます。
- 承認カードは `pending → succeeded／failed／denied／expired`（自動承認は `decision=auto` で直接 succeeded／failed）へ遷移し、既定24時間で期限切れ、新しい発話や再生成のたびにそのルームの承認待ちは `superseded`、停止した生成の未紐づけの提案は `cancelled` になります。決定 API は、所有者以外の行と、回答の保存にまだ結び付いていない行（`assistant_message_id IS NULL`）を「見つからない」として扱います。生成中に作った行は、回答の保存と同じトランザクションで初めて結び付き、それまでは承認 API から操作できません。決定済みの行への再送は、同じ決定なら冪等に同じカードを、異なれば 409 を返します。実行は SAVEPOINT の中で行い、失敗しても決定自体は確定させ、行とカードを `failed` として理由コードを残します。
- 共有チャットの閲覧と fork では、承認カードを ID・ツール名・ファミリー・状態・決定だけの読み取り専用に伏せます。提案の中身（非公開のメモ本文や差分）・実行結果・警告は見せません。

## 影響

- 新しいツールを1つ追加するたびに、ファミリー・引数モデル・プレビューの形・実行ハンドラを1か所（`services/chat_workspace_tools/<family>.py`）へ足し、`services/response_models.py` の Literal（対応ツール名・プレビューの種類）を同時に広げます。カードの形が正本からずれると保存も配信もできません。
- 「常に承認」は取り消しにくい操作を確認なしにする機能なので、対象を増やすときは共有中の対象や外部データを読んだ直後の除外条件を同じように設けてください。無条件で自動実行を許す新しいツールを足しません。
- 画面操作エージェント（第14節）や MCP（第15節）と混同しないでください。前者はチャット外の画面操作専用の契約、後者は外部クライアントの事前同意が前提で、どちらもこの承認カードの仕組みを再利用しません。
- 承認待ちのまま応答が終わるターンが増えるため、テレメトリ（`workspace_write_proposals`・`workspace_auto_executions`・`approval_pending_turn`・`auto_approval_suppressed_by_untrusted_input`）で実際の承認率・自動承認の抑止頻度を追えるようにしています。抑止が多すぎる、または少なすぎる場合はこの判断を見直してください。
- 本人以外の書き込みが起きないよう、承認 API・実行ハンドラのすべてのクエリは利用者 ID で絞ります。新しいツールの実行ハンドラも同じ境界を通してください。

### 改訂: 対象をメモ以外（公開 Prompt・自分用 Prompt・個人 Skill）へ広げる（2026-09）

PR2 で、既定スキル「プロンプト共有と設定」（`users.prompt_tools_skill_enabled`）と、その配下のツール（`shared_prompt_read`・`my_prompt_list`／`my_prompt_read`・`my_skill_list`／`my_skill_read` の読み取り、`publish_prompt`・`my_prompt_save`・`my_skill_save` の書き込み）を追加しました。基本の設計判断（生成中は実行しない、承認カード経由、既定スキルとセットで出し入れ）は変えていません。以下は追加した対象に固有の扱いです。

- **公開 Prompt の作成のみ**: `publish_prompt` はテキスト Prompt の新規作成のみで、SKILL 投稿・画像・Resources・既存の公開投稿の編集や削除には対応しません（既存の投稿画面に任せます）。承認前は `prompts` テーブルへ何も保存せず、下書きは承認行の `arguments`／`preview` にだけ持ちます。承認実行時に Web 投稿フォーム（`blueprints/prompt_share/prompt_share_api.py`）と同じレート制限（8件/ユーザー/時、12件/IP/時、15秒のユーザー別クールダウン）を共有モジュール `services/prompt_create_limits.py` 経由で適用し、チャット全体の書き込み上限（`chat_tool:write:user`）にも重ねて従います。MCP 経由の投稿（`services/mcp_config.py`）は別の上限のままです。`publish_prompt` は「常に承認」を許可しません（`allows_always=False`）。
- **自分用 Prompt（Task）・個人 Skill の作成／編集**: `my_prompt_save`・`my_skill_save` は、ID を省けば新規作成、指定すれば既存の自分の行を編集します。編集は提案時に読んだ `updated_at` を版として承認実行時に再確認し、その間に別画面で更新されていれば `target_changed` として失敗させます（メモの `revision` と同じ役割を、Task／個人 Skill では更新時刻で代替）。両ツールとも「常に承認」を許可します。一覧ツール（`my_prompt_list`／`my_skill_list`）は ID・題名・更新時刻だけの軽量な索引で、本文はページ付きの `my_prompt_read`／`my_skill_read` を別に呼んで読みます（メモの list／read 分割と同じ形）。ON/OFF の切り替えと削除はツールを用意していません。
- **非公開内容の混入警告**: `publish_prompt` の提案内容が、そのターンで読んだ非公開のテキスト（メモ本文・抜粋、自分の Task／個人 Skill 本文、`llm_profile_context`）と 50 文字以上そのまま一致した場合、`services/chat_workspace_tools/private_overlap.py` の突き合わせでカードに警告（`private_text_in_public_post`）と一致箇所を出します。`my_prompt_read`／`my_skill_read` はページ単位のチャンクで返るため、`PrivateTextTracker` は隣接するチャンクを継ぎ合わせてページ境界をまたぐ一致も検出します。ブロックはせず、利用者が確認チェック（`ToolApprovalDecisionRequest.acknowledge_warnings`）を入れるまで承認 API 側で 400 を返して先へ進めません。
- **外部内容の扱い**: 他人の公開投稿を読む `shared_prompt_search`（既存の事前検索ツールを流用し、対応スキルが ON かつ `use_shared_prompts` が未選択のターンにだけ検索クロージャを補う）と `shared_prompt_read` は、どちらも `services/chat_generation.py` の外部内容ツール集合に含め、読んだターンは「常に承認」があっても手動カードへ戻します。一方、自分の Task／個人 Skill の読み取りはメモと同じく「自分自身のデータ」として扱い、`get_evidence` の再読み取り判定でも外部内容にしません。

## 影響（改訂分）

- 新しい対象を1つ広げるたびに、所有者確認・提案時の版比較・「常に承認」の除外条件を既存の対象と揃えてください。特に公開投稿を伴うツールは、既存の投稿経路（Web／MCP）のレート制限と重複なく・矛盾なく適用できるかを確認します。
- 非公開内容の混入検出は簡易な文字列一致（`difflib` によるブロック一致、50 文字以上）であり、言い換えや要約された引用は検出できません。誤検知・見逃しのどちらもあり得る前提の「確認を促す警告」であり、公開の可否を機械的に判定するものではありません。
