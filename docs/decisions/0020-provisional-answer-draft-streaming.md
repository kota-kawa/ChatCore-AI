# 0020: 判断ステップの本文は、確定前に表示専用の下書きとして先に流す

## 状態

採用

## 背景

判断ステップの本文は、ツール呼び出しで終わらないと分かるまで配信も保存もしません（[0006](0006-long-running-chat-completion-recovery.md)）。全文をバッファするのは、一時障害時に先頭から再試行する、ツール呼び出しで終わった判断の前置きを捨てる、Qwen が回答の前に流す `</think>` までの下書きを除く、タグ無しの封筒 JSON を回答と取り違えない、メモ書き込みの申告を裏付けと照合する、空回答を回復する、といった判断が全文を前提にしているためです。

その結果、検索しない回答でも最初の文字はストリーム終了後に出ていました。実測では、最初のトークンから画面に出るまでおよそ 1〜1.8 秒かかり、回答が長いほど伸びます。

## 判断

- 全文バッファと確定処理（保存、`state.chunks`、引用・画像・生成 UI の解決、回復）は変えない。
- その横で、ガードを通した本文を表示専用の `answer_draft`（`{"text": 差分}`）として先に流す。下書きは `state.chunks`・`_chunks`・保存・`streamed_display_text`・トレースに入れない。
- 下書きを捨てるとき、および確定で置き換えるときは `answer_draft_reset`（空のペイロード）を流す。確定時は `answer_draft_reset` の後に、従来どおりの `chunk` を流す。
- 判定は `services/chat_answer_draft.py` の純粋な判定器が持つ。内部の封筒は除き、見える文字が一定数たまるまで保留する。先頭が `{` またはコードフェンス付き JSON のステップはタグ無しの封筒の可能性があるため下書きしない。コード外に `</think>` が現れたら下書きを取り消してその後ろから再開する（確定時の `strip_leaked_reasoning_chunks` と同じ規則で、モデル別の配信経路は作らない。[0009](0009-single-turn-state-chat-loop.md)）。引用マーカーは下書きでは表示せず、確定時にチップへ置換する。
- メモなどの書き込みツールがあるターン（`_workspace_tools` あり）では下書きを一切出さない。
- 保留バッファを空にする、または差し替える箇所では、見せた下書きがあれば `answer_draft_reset` を先に流す。取り消しは冪等で、停止経路と生成スレッドの競合でも取り消しが救済した `chunk` より先に並ぶ。
- フロントエンドは確定した本文の後ろに下書きを続けて描く。復元用に保存する本文と再開位置には下書きを含めない。

## 影響

最初の文字が、ストリームの終了ではなく本文の到着に合わせて出ます。ストリームで届く本文は下書きと確定の 2 回配信されるため、1 ターンのイベント数とリプレイ用の保持量が増えます。Redis のリプレイは順序どおりに再生するので、再接続しても下書き・取り消し・確定の関係は保たれます。

下書きを書き込みツールのあるターンから外すのは、裏付けのない「追記しました」のような申告が、取り消されるとしても一瞬でも見える事故を避けるためです。この判断は、確定処理が申告を裏付けと照合する前提（[0013](0013-chat-writes-through-stored-approvals.md)）を保ちます。

利用者に取り消しが見えうるのは次の場合です。見せた文字が消える回数は生成テレメトリの `answer_draft_resets` で、最初の文字までの時間は `first_visible_text_ms` で追えます。

- 前置きを書いたあとにツールを呼んだ判断（前置きは回答ではない）。
- Qwen の `</think>` までの下書き。
- 一時障害の再試行、ツール拒否の引き直し、入力超過の再実行。
- プロトコル漏れで確定が全文を置き換えるとき。

保留の文字数に満たない前置きは下書きされないため、短い前置きだけでツールを呼ぶ判断は取り消しが見えません。取り消しの実際の頻度は運用ログの上記指標で確認し、多ければ保留の文字数を見直します。実行経路と契約の正本は [ARCHITECTURE.md](../../ARCHITECTURE.md) の「チャット生成と SSE」です。
