# 0023: チャットから抽出した記憶は承認を待たず、未確認の事実として自動保存する

## 状態

採用。[ADR 0016](0016-context-fact-confirmation.md) の確認状態の規則はそのまま使い、「抽出した内容は承認するまで保存しない」という運用だけを置き換えます。

当初は、有効な事実が上限（200 件）に達して保存できない分だけを承認待ち候補に残していました。確認と編集を記憶の画面に一本化する方針（[ADR 0025](0025-always-on-memory-with-provenance.md)）に合わせ、この点を改めました。上限のときは承認待ちを作らず、手を入れていない自動保存の事実を無効化して入れ替えます（下の「判断」の 3〜5 項目目と「影響」）。題名と、未確認で自動保存するという判断は変えません。

## 背景

チャットから抽出した記憶（`context_facts`）の候補は、利用者が承認して初めて保存される仕組みでした。抽出は確信度 0.9 以上・重要度 80 以上・本人発話の逐語引用・秘密情報の除外を通ったものだけを返しますが、候補一覧は記憶の画面の奥にあり、初期設定も無効（`users.context_auto_extract_enabled` が FALSE）でした。そのため、機能を知っている一部の利用者を除いて、記憶がほとんど育たず、記憶を使った回答の利点が出ていませんでした。

## 判断

- 抽出基準（プロンプト・しきい値・モデル）は変えず、基準を通ったものは承認を待たず `context_facts` へ保存します。`source_kind` は `chat`、`confidence` は抽出時の値、`source_ref` は従来どおり `chat:{room_id}:message:{assistant_message_id}` です。
- 自動保存した事実は本人未確認（`last_confirmed_at` が NULL）で保存します。確認済みとして保存しないので、ADR 0016 の自動実行の抑止（未確認の事実を検索したターンは書き込みツールの「常に承認」を自動実行しない）はそのまま働きます。本人が Web UI で編集すれば確認済みになる規則も変えません。
- 保存は 1 トランザクション・利用者単位の advisory lock の中で、設定の確認 → 重複判定 → 事実の挿入、の順に行います。有効件数が上限なら、挿入の前に 1 件を無効化して入れ替えます。重複判定は BM25 と fingerprint で、比較対象は「有効な事実」「本人が無効化した事実（`deprecated_reason` が `user` または未記録）」「本人が却下した候補」です。このため、利用者が無効化した（取り消した）内容は再び保存されません。上限で外れた事実（`capacity`）と、承認待ち・承認済みの候補は比較しないので、上限で外れた内容が再び話題に出れば新しい事実として保存できます。有効な事実と重複したときは、事実の行を更新せず出典だけを足します（ADR 0016 の出典の扱いと同じです）。保存した事実には、候補の承認時と同じく埋め込みを予約します。
- 有効な事実が上限（200 件）に達しているときは、`source_kind` が `chat` で `last_confirmed_at` が NULL の事実（自動保存のまま本人が手を入れていないもの）のうち、最後に話題に出た時刻が最も古いものを `deprecated`（`deprecated_reason` は `capacity`）にして入れ替えます。最後に話題に出た時刻は出典の `observed_at` の最大値で、出典が無い事実は `created_at` です。同じなら重要度が低いもの、それも同じなら `id` が小さいものを選びます。本人の手入力・編集・承認、MCP、import 由来の事実と、同じバッチで保存・再言及したばかりの事実は選びません。対象が 1 件も無ければ、新しい内容は保存せず、承認待ちにも入れません。入れ替えられた事実は記憶の画面の「無効化済み」に理由つきで残り、本人が復元できます。
- 承認待ち候補への挿入と、その一覧・承認・却下の API と画面は取り除きました。抽出を走らせる条件は「設定が有効」だけです（上限でも入れ替えと再言及の記録があるため）。すでに溜まっていた承認待ちは、同じ抽出基準を通ったものなので、利用者ごとに有効件数の空きまで、重要度・確信度の高い順に未確認の事実（`source_kind` は `chat`、埋め込みは生成待ち）として移しました。移しきれなかった承認待ちは、migration の安全検査が `DELETE` を許さないため、そのまま残して使いません（テーブルは却下済みの候補を重複判定で読むために残し、削除は後続の変更で行います）。
- 保存したことは、チャットの中では知らせません。回答の下の通知や専用の読み取り API は作らず、確認・編集・無効化は記憶の画面に一本化します。取り消しは、記憶の画面での無効化（既存の記憶の更新で `status` を `deprecated` にする）で行い、新しい書き込み API は作りません。
- 自動抽出は初期オンにします。新しい migration で列の初期値を TRUE にし、既存の利用者も全員 TRUE にします。過去に自分でオフへ戻した利用者もオンになります。

## 退けた案

- **完全な承認制の維持**: 記憶が育たない現状が続きます。承認の手間が理由で価値のある記憶が捨てられるうえ、候補一覧を見に行く動機がありません。
- **確認済みとして保存**: 本人が見ていない内容を確認済みにすると、ADR 0016 の「未確認の事実を根拠にした書き込みを自動実行しない」という防御が効かなくなります。
- **確信度のしきい値で、直接保存と承認待ちに分ける**: 抽出基準はすでに高い確信度（0.9 以上）で絞っており、その内側で分ける根拠になる実測がありません。2 本の経路ができ、利用者にも説明しにくくなります。
- **抽出の下限を下げて保存量を増やす**: 品質の確認なしに誤った記憶を増やします。この変更は抽出内容を変えず、保存先だけを変えます。
- **回答の下で保存を知らせ、その場で取り消せるようにする**: 保存のたびに表示すると、回答を読む邪魔になり、利用者にも毎回の確認を促します。自動で保存・管理し、確認と編集を記憶の画面に集めるほうが、仕組みを単純に保てます。この案は一度実装しましたが、採用せず取り除きました。

## 影響

- MCP の `get_personal_context`・`search_context` に、未確認の自動保存分が現れます。外部クライアントは `last_confirmed_at` が NULL であることで、本人が確認済みの事実と区別できます。
- 抽出の LLM 呼び出し（GPT-6 Luna、利用者の費用として計上）が、利用者全員の通常ルームの各ターンに増えます。デモ用アカウントも新規ユーザーの初期値を引き継ぐので抽出が走りますが、費用はデモの期間全体の上限に含まれ、保存した記憶はアカウントと一緒に削除されます。
- migration `20261119_01` は列の初期値を TRUE にし、全員を TRUE へ更新します（expand のみ。旧バージョンのコードは列を読むだけなので、適用中に旧色が動いても壊れません）。downgrade は初期値を FALSE に戻すだけで、個別の設定値は復元できません。upgrade が全員を TRUE にするため、元がオフだった利用者を区別できないからです。
- 自動保存分を取り消した後に、同じ内容が別の言い回しで再び抽出されたときの扱いは、BM25 の類似度に依存します。比較対象の件数上限（500）を超えるほど無効化した事実が溜まると、古い取り消しは比較から外れます。
- 上限に達している利用者では、新しい内容が入るたびに、古い自動保存分が無効化されます。保存できるのは入れ替え対象がある間だけで、すべて本人が手を入れた事実になれば、それ以上は自動保存されません。入れ替えられた事実は無効化済みの一覧から復元できますが、有効な事実が上限のあいだは復元できません。
- migration `20261120_02` は `context_facts.deprecated_reason`（無効化の理由）を追加します。CHECK には、後続の変更が使う `superseded`・`merged` も最初から入れています（値を後から足すには制約を削除する必要があり、安全検査に落ちるため）。理由が NULL の無効化済みの事実（この列の追加前の記録）は、本人が無効化したものとして扱います。
- migration `20261120_03` は、溜まっていた承認待ちを上記の規則で事実へ移します（expand のみ。旧バージョンのコードが同時に動いていても、同じ利用者単位のロックを取ってから件数を数えるため、上限を超えません）。downgrade では移した事実を戻しません。デプロイ後は、移した事実の埋め込みを `python3 scripts/backfill_embeddings.py --target facts` で作ります（`embedding_status = 'pending'` の行が対象です）。旧バージョンのコードは `deprecated_reason` を書かず、上限時に承認待ちを作ることがありますが、新しいコードはそれらを読まないので害はありません。旧コードが復元した事実に古い理由が残っても、API は無効化済みの事実にだけ理由を返します。
- 利用者に自動保存を知らせる経路は、記憶の画面だけです。画面を開かない利用者は、何が保存されたかに気づきません。記憶の画面に「未確認」の表示や「確認済みにする」操作もまだなく、自動保存分が未確認であることは、現状は MCP の応答とチャットの自動実行の抑止にだけ現れます。
- 実装は `services/repositories/context_fact_candidate_repository.py`（`store_extracted`）、`services/context_vault_candidate_service.py` にあります。自動保存の設定のスイッチは `frontend/components/memo/ContextExtractionSetting.tsx` で、記憶の画面（`MyContextPanel`）に置きます。
