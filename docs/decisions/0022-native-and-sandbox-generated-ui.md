# 0022: 宣言的UIとsandbox Artifactを併用する

## 状態

採用

## 背景

比較・図解・試算を毎回HTML/JavaScriptで生成すると、トークン数と検証・修復の負担が増える。一方、自由なシミュレーションや3Dには既存Artifactの表現力が必要になる。選択ボタンは会話の回答を選ぶ標準部品であり、ローカルの計算条件と書き込み承認とは異なる役割を持つ。

## 判断

- バージョン付きの宣言的UIを追加し、既存Artifactを維持する。モデルは許可された部品・レイアウト・式を組み合わせる。ネイティブレンダラーに任意HTML・CSS・JavaScriptや任意APIへの操作を渡さない。
- ノードと式をIDで参照する非再帰のJSON契約とする。Pydanticから既存の生成器でZodを作り、両境界で構造と参照・計算量を検証する。
- Skill事前選択の同じ呼び出しで回答形式を決める。通常の比較・図解・入力付き計算は宣言的UI、自由なシミュレーションと3DはArtifactを選び、混合も可能にする。
- 完成したブロックだけを既存SSEで順次公開し、本文との順序をmessage_partsへ保存する。生成ID・連番・終了時の一度だけ保存という契約を変えない。
- 宣言的UIは検索画像と共存する。Artifactの画像排他とiframe/CSPは維持する。新UIの画像も選定済み画像への署名付き中継参照に限定する。
- 選択ボタンと新UIの会話操作は入力欄への反映に統一する。ユーザーの通常送信後に既存Agentと書き込み承認を通す。生成UI設定OFFでも標準ボタンは残し、明示的なテキスト限定指定では文章化する。
- 選択状態だけを同じブラウザ・利用者・通常ルーム・回答・UI定義の範囲で復元する。自由文・数値・スライダー値は保存しない。共有先へ操作状態を渡さず、共有ではローカル操作だけを許す。
- HTTP配信時の能力通知がないクライアントにはfallbackテキストへ変換する。保存とRedisの正本は変換せず、新旧クライアントが同じ履歴を参照できるようにする。

## 影響

新UIの定義は既存のmessage_partsへ保存できるためmigrationは不要。宣言的UIの部品と式の追加は契約の更新を伴い、旧バージョンの読み取りとfallbackを維持する。生成されたコードをiframe外へ移す変更や、既存Artifactを新UIの制約へ合わせる変更は行わない。
