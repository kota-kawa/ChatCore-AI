# 0009: 通常チャットを単一 TurnState と単一判断ループで実行する

## 状態

採用

## 背景

通常チャットの検索フローでは、検索前の Planner、調査中のステップメモ、調査完了ノート、最終回答用 Summary が別々の状態とフェーズを作っていました。同じ質問の目的や根拠が複数の表現へ複製されるため、更新漏れや相互矛盾が起きやすく、検索履歴が長くなるほどコンテキスト管理も複雑になっていました。また、固定長の抜粋や先頭・末尾保持では、文字数は抑えられても質問に必要な情報が残る保証がありません。

モデル別の問題をプロンプトや別ワークフローで補う方法も、検索判断と回答判断を分断し、プロバイダ追加時の挙動差を大きくします。必要なのはフェーズごとの要約ではなく、そのターンで現在分かっていることを根拠付きで更新し続ける共通の状態です。

## 判断

- 通常チャットの1ターンにつき、`services/research_state.py` の `TurnState` 1つを意味状態の正本にする。状態には目的、未解決事項、得られた事実、出典、実行済み検索を含める。`step_notes` と `research_summary` は別状態として保持しない。
- `services/chat_generation.py` が実行フローを1本の判断ループとして所有する。メインモデルは `TurnState` を見て「検索する」または「回答する」を選ぶ。検索した場合は、その結果を受け取った同じモデルが `TurnState` を更新し、同じループで再判断する。事前の検索 Planner、検索終了時だけの Wrapup、独立した Summary 生成ループは設けない。
- 状態更新は通常の要約や文字数による切り詰めとして実装しない。モデルが質問との関係を判断し、新しく分かったこと、既存情報の修正、まだ分からないことを根拠とともに統合する。
- 検索結果の全文と元のツール結果は、既存の `WebSearchResult` と `web_search_results_by_key` などを使ってターン状態の外かつプロンプト外に Evidence として保持する。`TurnState` は回答に必要な事実、出典情報、Evidence への安定した参照を持つ。次の判断で生の検索履歴は原則再送せず、詳細が必要になった場合だけモデルが Evidence を参照 ID で再取得できるようにする。
- ループの終了条件は、メインモデルが回答可能と判断した場合、または検索上限へ到達した場合の2つだけにする。検索上限へ達した場合も別の締めフェーズへ移らず、その時点の `TurnState` と必要に応じて再取得した Evidence から回答する。
- モデル／プロバイダ固有処理は `services/llm.py` と `services/llm_tool_schema.py` の薄い Adapter に限定する。Adapter はツール形式、ストリーム表現、出力上限などの機械的差異を共通契約へ変換する。Qwen を含む特定モデルのために別の検索判断、状態、フェーズ、プロンプトワークフローを持たない。

この判断は [ADR 0007](0007-research-turn-answer-contract.md) のうち、検索 Planner、ステップメモ、調査完了ノート、締めステップ、フェーズ別投影による調査オーケストレーションを置き換えます。ADR 0007 に含まれる入力上限の検出、回答本文の継続生成、SSE の保存・配信契約はこの判断の対象外であり、引き続き有効です。[ADR 0006](0006-long-running-chat-completion-recovery.md) の限定継続による部分回答回復も変更しません。

## 影響

- 検索の有無にかかわらず、通常チャットは同じ状態契約と制御ループを通ります。検索判断と回答判断が同じモデルに戻るため、Planner とメインモデルの意図のずれをなくせます。
- Evidence の保持期間、容量上限、アクセス制御は `TurnState` と分離して管理する必要があります。再取得は現在のターンと利用者の権限へスコープし、モデルから任意の他ターンの Evidence を読めないようにします。
- `TurnState` の更新が構造契約を満たさない場合は、同じ状態に対する検証・修復として扱います。修復専用の調査フェーズや第2の意味状態は作りません。
- 検索上限は費用とレイテンシの安全境界として残ります。上限到達は「調査完了」を意味しないため、回答では残る未解決事項や不確実性を反映します。
- プロバイダ Adapter を越えるオーケストレーション契約は共通になります。新しいモデルの追加時は、まず共通ループで動作させ、モデル固有フローを増やさず Adapter の機械的変換だけを検討します。
