# 0008: ツールスキーマの検証をプロバイダに委ねない

## 状態

採用

## 背景

Groq の `openai/gpt-oss-120b` で、調査フェーズのストリームが再試行不可のエラーで打ち切られ、チャット生成そのものが失敗しました。

```
Tool call validation failed: parameters for tool web_search did not match schema:
errors: [`/search_language`: value must be one of "", "ar", ... "zh-hant"]
```

原因は、`web_search` ツールの `search_language` に宣言していた `enum` です。Brave Search の日本語コードは ISO 639-1 の `ja` ではなく `jp` であり、モデルが自然に `ja` を返した時点で列挙の外になります。

問題は綴りの食い違いだけではありませんでした。

- OpenAI 互換プロバイダの一部（Groq）は、モデルが返したツール引数をサーバー側で JSON Schema 検証します。違反はストリーム途中の `APIError` として返り、`LlmProviderError`（retryable=false）へ落ちて、そのターン全体が「内部エラー」で終わります。ツール引数1つの些細な逸脱が、会話の失敗と同じ重さになっていました。
- 同じ致命性は `enum` 以外にもありました。`required` は引数の欠落で、`additionalProperties: false` はモデルが `count` のような独自の引数を1つ足しただけで、同じ拒否を引き起こします。
- アプリ側は元々これらの値に寛容でした。`_normalize_requested_search_language` は未知の言語を空文字へ落として入力言語の推定へ委ね、空のクエリはツール結果としてモデルへ差し戻します。つまり厳格な `enum` は、こちらが優雅に扱えたはずの値をプロバイダに致命傷へ変えさせていただけでした。
- 一方でツール呼び出し経路の `freshness` は正規化されておらず、モデルの言い換え（`past week` など）がそのまま Brave のクエリへ載る余地が残っていました。プランナー経路だけが検証を持ち、契約が二重化していました。

## 判断

- プロバイダへ渡すツールスキーマは `services/llm_tool_schema.py` が境界で緩める。`enum` / `const` / `required` を落とし、`additionalProperties: false` は `true` にする。落とした情報は各引数の説明文へ「Allowed values: ...」「Required.」として移し、モデルへの誘導は保つ。`type` と `description` は残す。
- 緩和は OpenAI 互換と Claude の両方に同じ形で適用し、モデルへ見せる契約をプロバイダごとに変えない。値の解釈はどのプロバイダでも同じハンドラが行う。
- ツール引数の検証と正規化は、優雅に劣化できるアプリ側に一本化する。検索言語は ISO / BCP-47 の揺れ（`ja`、`ja-JP`、`zh-TW`、`fr-FR`）を Brave のコードへ寄せ、解決できない値は空文字にして入力言語の推定へ委ねる。鮮度指定はプランナー経路とツール呼び出し経路で同じ `normalize_web_search_freshness` を通し、外部 API へ渡る直前でも再度正規化する。引数の型が揺れても実行を止めない。
- それでもプロバイダがツール呼び出しを拒否した場合に備え、`LlmToolSchemaError` を独立した例外として分類する。同じ要求の再送は同じ拒否になるため再試行可能とはせず、回復手段は「同じステップをツールなしで1度だけやり直す」ことにする。ターンを落とさず、手持ちの情報で回答へ進む。

## 影響

- ツール引数の綴り違い・欠落・余分な引数でチャット生成が失敗しなくなります。想定外の値は既定へ丸められ、必要ならツール結果としてモデルへ差し戻されます。
- 許可値の一覧が説明文へ移るため、リクエストのプロンプト長がツール定義ぶんだけ増えます（`web_search` で数百文字程度）。
- 新しいツールを追加するときは、スキーマの制約に検証を期待しないでください。制約は誘導であり、実際の検証はハンドラ側に書きます。
- `tool_schema_recoveries` を1ターン分の生成テレメトリへ追加しました。拒否がどれだけ起きているかは構造化ログで追えます。
- 外向き MCP サーバー（`services/mcp_server.py`）は逆向きの境界であり、この判断の対象外です。そちらは不正なカテゴリを許可値付きのツールエラーとしてクライアントへ返す既存の扱いを維持します。
