# 0019: チャットの再接続を回答ごとの生成IDに固定する

## 状態

採用

## 背景

部屋単位の Redis 履歴には複数の回答が残る一方、イベント番号は回答ごとに1から始まっていました。2回目の生成中に別ワーカーへ再接続すると、前回の完了通知で今回の表示を上書きできました。ローカルの完了済みジョブを優先する経路にも同じ問題がありました。保存は生成側で進むため、画面だけが古い回答になり、再読込すると正しい回答へ戻ります。

## 判断

- 生成 ID とイベント番号の組を再接続位置の契約にする。生成 ID はチャット所有者と部屋の境界内で扱い、アクセス確認を省略しない。
- クライアントは送信前に生成 ID を決め、開始リクエストと再接続で使う。初期レスポンスを失っても、前回の最新ジョブへ接続しない。
- Redis の履歴・通知を生成 ID ごとに分け、最新 ID の参照と部屋単位の生成ロック・停止要求を分離する。指定された ID が無ければ別の生成へフォールバックしない。
- ブラウザーの下書きとイベント番号は、生成 ID が一致する場合だけ復元する。

## 影響

連続送信・再生成・編集再生成をまたいで回答が混ざらなくなります。ID を指定しない既存クライアントは最新生成へ接続できますが、旧形式の部屋単位の Redis 履歴は再利用しません。リプレイ履歴には既存の保持期限を適用し、DB スキーマと LLM への入力は変更しません。

実行経路と契約の正本は [ARCHITECTURE.md](../../ARCHITECTURE.md) の「チャット生成と SSE」です。
