# 0024: 回答の実行記録を本文から分け、回答パーツとして構造化する

## 状態

採用

## 背景

「回答までのステップ」（検索・参照元の検索・ページ読取などの実行記録）は、サーバーが HTML に組み立てて回答本文の先頭へ前置し、その文字列ごと保存・配信していました。表示、モデルへ戻す履歴、画像の挿入位置、生成中の文字送り、出典チップの除去は、それぞれが本文から HTML を切り出して扱っていました。切り出しは Python と TypeScript の両方にタグの数え上げとして重複し、生成中の二重表示、履歴からモデルへの混入、出典の favicon の欠落といった不具合が、切り出しの漏れとして続いていました。

## 判断

- 実行記録は本文に混ぜず、回答パーツの 1 種類（`answer_trace`）として構造化データのまま保存・配信する。形・上限・検証は `services/answer_trace.py` が持ち、ステップは安定した ID・種類・状態（実行中／完了／失敗）・出典を持つ。モデルの内部の推論は含めない。
- 保存先は既存の回答パーツ（`chat_history.message_parts`）とし、DB スキーマは変えない。本文の列には文章だけを保存する。別テーブルにする案は、回答と記録を別々に読む用途が無いので採らない。
- 生成中は専用の SSE イベント `answer_trace_updated` で記録全体のスナップショットを送る。差分にしないのは、再接続・再送・順序の入れ替わりがあっても、最後に届いたものを表示すれば足りるようにするため。既存のパーツ更新イベントに載せる案は、そのイベントが本文の書き換えと下書きの取り消しを伴うため採らない。終端イベントのパーツには記録を含め、確定後の表示はそれを正とする。
- 描画は画面側が構造化データから行う。マークアップは構造化前と同じにし、見た目と開閉の操作は変えない。
- 構造化前に保存された回答は書き換えない。読み出す境界（`services/repositories/chat_repository.py`）で本文先頭の HTML を切り離し、`legacy_answer_trace` パーツとして渡す。本文から記録を切り出す処理はこの境界にだけ置く。読み出した回答を別のルームへ複製するときは、このパーツのまま保存する。一括で書き換える移行は、解析に失敗した行の履歴を壊しうるので採らない。
- モデルへ渡す文章から Web 検索の表示ブロックを取り除く処理（`strip_web_search_sources_html`）は残す。DB を通らない一時チャットの履歴と、さらに古い「参照サイト一覧」だけの回答が、表示用の HTML を本文に持つため。
- 記録だけの応答は回答として扱わない。空回答の判定では、検索画像と同じく記録のパーツを数えない。

## 影響

本文（保存する `message`、配信する `response` とテキストパーツ）に表示用のマークアップが入らなくなり、コピー、モデルへ戻す履歴、生成UIの修復で渡す前回出力も文章だけになります。生成中に利用者が開いた記録は、本文が伸びても閉じません。

構造化前の回答は、読み出すたびに境界で変換されます。ブラウザに保存された構造化前の履歴と、一時チャットに残っている構造化前の回答は変換されず、従来どおり本文の中の HTML として表示されます。古い画面を開いたままの利用者は、再読み込みするまで新しい回答の記録が表示されません（本文は表示されます）。記録の文言は従来どおりサーバーが日本語で作り、画面の表示言語には連動しません。

実行経路と契約の正本は [ARCHITECTURE.md](../../ARCHITECTURE.md) の「チャット生成と SSE」です。
