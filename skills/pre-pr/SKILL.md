# PR を作るまで

規則の正本は `AGENTS.md` の「コミットおよびプルリクエストのガイドライン」と「エージェントの作業ルール」、レビュー担当のモデルは `docs/knowledge/development_conventions.md` の「サブエージェントの指定」です。

## 1. コミットを整える
- `main` に直接コミットしていないことを確認する。
- バグ修正とリファクタリング、機能追加と無関係な整形のように種類の違う変更は、別々のコミットに分ける。
- 件名は「日本語の要約 / English summary」。何をどう変えるかが件名だけで伝わるようにし、「修正」「改善」「対応」だけの件名にしない。理由や制約の説明が要るときだけ、空行を挟んで本文に日英で書く。
- `git add` には明示的なパスを渡す。`next dev` が書き換える `frontend/next-env.d.ts` は戻す。

## 2. 検証する
- 変更箇所と、直接影響を受ける範囲のテストだけを実行する。コマンドと結果を控えておく。
- UI を変えた場合は `ui-verify` Skill で Before/After を揃える。
- AI の出力が変わる場合は `ai-output-check` Skill で変更前後を比較する。
- 構成・責務・リクエスト経路・データや契約の境界を変えた場合は、`ARCHITECTURE.md` の該当章と図、`README.md` の対応する図が実装と合っているか確かめ、ずれていれば同じ PR で直す。

## 3. 独立レビュー（コードを変えた場合）
- 「サブエージェントの指定」にあるレビュー用サブエージェントに、次の 3 つだけを渡す。実装の意図や経緯は渡さない。
  - スコープ: 合意した要件とスコープ外
  - 差分: `git diff origin/main...HEAD` の範囲
  - チェックリスト: 要件を満たす／関連範囲への影響を確認している／全体の整合性・保守性を損ねていない／スコープ外の変更が無い／不要なコードが無い／テストが通る／禁止事項に触れない
- 指摘はそのまま採用せず、コードを読んで確かめてから反映する。反論があればユーザーに伝える。
- 修正とテストの繰り返しは 5 回までにする。超えたら、未解決の点を添えてユーザーに報告する。
- ドキュメントだけの変更ではレビューを省略してよい。省略したら PR 本文にそう書く。

## 4. PR を作る
- タイトルはコミット件名と同じ形式（日英併記）。
- 本文は日英両方で書き、コードを読まない人が判断できるように次の順で並べる。各項目は数行に収め、該当しない項目は省く。
  1. 解決する問題と変更後の挙動（必要なら変更前後の具体例）。関連 issue があればここに付ける。
  2. 影響する経路と守る契約、スコープ外にしたもの
  3. この方針を選んだ理由（退けた案があれば一言）
  4. 検証: 実行したテストのコマンドと結果、テストで担保できていない範囲、実施しなかった確認とその理由。UI を変えた場合は Before/After の画像と実描画で確認した条件、AI の出力が変わる場合は比較の入力・観点・結果とテレメトリの指標。
- ファイルごとの変更の列挙や、差分から自明な実装の説明は書かない。
- 確認していないことを確認済みと書かない。
- `git push -u origin <branch>` の後、`gh pr create --base main` で作る。
- PR はマージしない。
