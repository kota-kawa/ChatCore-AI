# AI 出力の品質確認

対象・比較方法・確認できる範囲の限界は、`docs/knowledge/development_conventions.md` の「AI 出力の品質確認」が正本です。最初に読み、この手順と食い違ったら文書に従ってください。

## 手順
1. 対応するテストを決める: 同じ節の表から、変更した領域（プロンプト文言、ツール定義、生成ループ・予算、Web 検索、生成 UI、モデル設定）に対応するテストを選んで実行する。
2. 入力を固定する: 代表的なケースを 3〜5 件用意する。通常のケース、改善を狙ったケース、退行しやすいケース（長い文脈、ツール呼び出しが要る質問、日本語と英語の混在など）を入れる。Web 検索が関わる場合は、検索結果も固定し、文書の手順で機械的に検証してから使う。固定したデータは、比較結果を見て作り直さない。
3. 観点を先に決める: 例として、指示への追従、事実性と出典、形式（JSON やツール呼び出しの契約）、冗長さ、口調。
4. 変更前後を比べる: 変更前と変更後のプロンプト・ツール定義・会話を実装と同じ手順で組み立て、`sonnet-high` サブエージェントを LLM の代わりにして、同じ入力に対する出力を得る。観点ごとにどちらが良いかを根拠付きで記録する。
5. テレメトリを並べる: 同じ入力を変更前後で流し、構造化ログから指標を集計する。

   ```sh
   python3 scripts/summarize_generation_telemetry.py --baseline <変更前のログ> <変更後のログ>
   ```

   `--since` で計測を始めた時刻以降に絞る。指標が悪化していたら、回答が良く見えても PR にしない。
6. 実 API を使う場合（ユーザーが指示したときだけ）: 先に「ターン数 × 1 ターンの費用」で見込み費用を伝え、許可を得てから直列で実行する。実行後は `provider_usage.cost_nano_usd` を合算して報告する。1 回だけで差が出たケースは 2〜3 回流し直してから判断する。

## PR 本文に書くこと
- 使った入力（Web 検索が関わる場合は検索結果も）、観点、変更前後の比較結果
- 実行したテストのコマンドと結果
- テレメトリ指標の変更前後
- この比較で確認できないこと（本番モデル固有の挙動など）
